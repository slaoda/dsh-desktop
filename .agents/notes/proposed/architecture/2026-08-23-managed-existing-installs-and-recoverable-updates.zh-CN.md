# Decision: 管理符合条件的既有安装并提供可恢复更新

Status: proposed
Category: architecture

## 问题

原版桌面应用只拥有应用托管的 Harness 版本，并明确不读取 Harness 用户数据。Windows 管理器产品需要原地管理符合条件的既有安装，也需要通过备份配置和会话来实现可恢复更新。若缺少明确的所有权模型，这两项能力都可能误删外部文件、暴露凭据，或提交一个无法工作的版本切换。

## 方案

增加两项边界严格且需要用户主动选择的能力：

1. 检测外部安装，验证官方包清单和包内 CLI，并按来源分类。项目内依赖和来源不明的 PATH 项保持只读。只有验证通过的 npm 全局安装可卸载，且卸载操作委托给对应包管理器，不能直接删除目录。
2. 通过白名单类别备份用户确认的 Harness 主目录，同时始终排除凭据。默认最多保留三个备份。版本切换作为带日志的事务处理，只有本机回环健康检查成功后才持久化候选版本选择。

下载的软件包不能提供迁移代码。已知迁移必须是管理器自有的白名单操作；未知的破坏性变更必须明确告警。

## 验收标准

- 检测逻辑不能让项目内软件包进入破坏性管理流程。
- 外部 CLI 解析结果不能逃逸已经验证的包根目录。
- 凭据不能进入备份、恢复、诊断或日志。
- 候选版本启动失败时，已提交的选择仍是旧版本。
- 能检测陈旧事务日志，且不删除用户数据。
- 主进程重新校验每个 IPC 路径、URL、模式和安装标识。

## 考虑过的替代方案

- 继续只管理应用自有版本。这样更安全，但无法满足已确认的原地管理需求。
- 将外部安装导入应用存储。这样会重复占用大量空间，也违背原地管理要求。
- 允许每个下载版本执行自己的迁移脚本。这会跨越信任边界，并允许未经审查的代码修改用户数据。
- 备份整个 Harness 主目录。这可能复制 API Key 和无关用户文件。

## 风险

- Harness 数据布局可能变化，因此需要保守的类别白名单和明确的部分备份提示。
- Windows 环境中的全局包管理器发现方式并不统一。
- 备份大小和磁盘可用空间可能差异很大。
- 只有在对应行为和测试完成后，才能修改根产品边界说明及审计规则。
