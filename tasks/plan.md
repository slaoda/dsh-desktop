# 实施计划：启动失败诊断与修复

## 概览

在现有启动控制器、Supervisor、备份、版本事务和诊断日志之上增加独立修复层。实现顺序按风险优先：先建立类型契约和纯分类规则，再证明插件隔离 Overlay 与事务恢复，随后接入单轮修复编排、精确版本重装和 GUI，最后执行安全与打包验证。

## 架构决策

- 修复器只执行封闭联合类型中的白名单动作，日志不能生成命令或任意路径。
- 插件自动修复通过管理器拥有的 `--patch` Overlay 设置 `disabled: true`，不改写用户 YAML，不自动卸载。
- 每轮启动用持久化事务约束为一轮修复、一次重试；异常退出后先回滚未完成动作。
- 最后一次成功基线仅保存允许文件的元数据和哈希，不保存配置正文或敏感文件信息。
- 外部安装复用诊断分类，但修复引擎拒绝所有写操作。
- 新 UI 复用现有主窗口、颜色和排版，不引入新的组件库或运行时依赖。

## 依赖关系

```text
共享契约与分类规则
  -> 基线与修复事务
     -> Supervisor 体检/健康检查
        -> 插件隔离与版本修复动作
           -> Controller 单轮编排
              -> IPC/Preload
                 -> Renderer UI
                    -> 打包 E2E 与发布准备
```

## 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| Harness 不同版本的错误文案变化 | 中 | 规则以结构化基线和有限特征组合判断；不确定时只诊断 |
| `--patch` 或 `--dump-config` 在旧版本不可用 | 中 | 按精确版本能力检测；不支持时降级为只诊断 |
| 插件错误日志指向错误目标 | 高 | 自动隔离要求唯一候选、基线变化和官方 entry id 交叉验证 |
| 修复期间应用退出或断电 | 高 | 所有写入前持久化事务；初始化优先恢复 |
| 诊断输出包含密钥 | 高 | 采集白名单、长度上限、主进程脱敏和植入测试 |
| 精确版本无法联网重装 | 低 | 优先缓存；不可用时停止，不升级替代 |
| UI 被复杂修复流程挤满 | 中 | 默认只显示结果摘要，详情折叠，决策按钮只在相关状态出现 |

## 不并行事项

共享契约、事务格式、Controller 编排和 IPC 必须顺序实现。UI 可在 IPC 契约稳定后单独推进。当前不使用子代理或并行工作树。

## 开放问题

无。用户确认规格后从任务 2 开始测试驱动实现。
